# CampusHub 前端重构总方案与分阶段实施 Prompt

## 1. 重构目标

将 CampusHub 从功能型课程项目升级为现代校园社区产品：视觉参考小红书网页端的图片内容发现体验与现代校园论坛的信息组织方式，但不照搬现有产品。目标是视觉有识别度、需求内容易浏览、业务操作清楚、状态和权限可信。当前只面向电脑浏览器使用，优先打磨桌面 Web（尤其常见笔记本与 1280–1440px 及以上视口）；窄窗口应优雅适配，但本轮不以手机端设计作为目标。

重构的核心原则：
- 统一设计语言，不把所有页面做成同一种模板。
- 按需求类别和交互模式差异化展示；Demand、DemandResponse、Order 不能混为一谈。
- 优先复用并渐进改造当前代码，避免无必要地重写后端、状态机或 API。
- 一次只完成一个阶段，完成后执行检查并总结，再进入下一阶段；不要一次性大范围推翻全部页面。

## 2. 已确定的产品架构与业务基线

### 全站结构
- 学生端使用统一的社区型外壳：**发现 / 我的互助 / 消息 / 发布需求 / 个人菜单**。
- 管理员后台采用独立布局与导航，不套用学生端的内容流布局。
- 统一导航、色彩、排版、状态标签、弹窗、表单和交互反馈；各业务页面可以有自己的内容结构。

### 首页与需求卡片
- 首页是混合需求信息流：默认中等密度，以桌面端规则三列网格为主，宽度变化时合理调整列数；不使用瀑布流，不为手机端单独设计一套布局。
- 图片突出，卡片图片统一 4:3，卡片尽量等高；标题和摘要限制行数，底部信息位置稳定。
- 有真实用户上传图片时展示第一张真实完整图片；无图片时展示中性分类占位，禁止用随机/生成图片冒充用户内容。
- 各类卡片突出不同信息：二手物品图、组队时间与已选/目标人数、跑腿任务与截止时间/校邻币奖励、求助问题与回答数量/解决状态。
- 底部显示发布者头像、昵称（可进入公开主页）及发布时间，信用分。

### Demand、Response、Order 的业务边界

- `Demand` 是公开需求及其生命周期；`DemandResponse` 是公开响应、报名或回答；`Order` 只表示正式的一对一履约。
- `EXPRESS` / `ERRAND` → `DIRECT_ACCEPT`：直接接单，创建 Order。
- `SECOND_HAND` / `STUDY_TUTORING` → `SELECT_ONE`：先公开响应，发布者选定一人后创建 Order。
- `TEAM_UP` → `SELECT_MANY`：发布者选择报名者，达到目标人数后完成 Demand 并按现有规则结算，不为队员创建 Order。
- `HELP` → `HELP`：多人回答，发布者采纳答案后完成 Demand；不创建 Order。
- `OTHER` 才允许用户从合理的 `DIRECT_ACCEPT` / `SELECT_ONE` / `SELECT_MANY` 模式中选择；不能选择 `HELP`。普通用户界面使用易懂的业务语言，不裸露内部枚举。
- 取消正式订单会关闭关联 Demand，不重新开放同一需求；要继续找人需要发布新 Demand。
- **订单只允许接单方取消**，且必须遵守后端业务约束。保留现有履约流程：接单方上传完成凭证并确认、需求方二次确认、现有超时自动完成规则或仲裁。
- SELECT_ONE 创建 Order 后：发布者能看完整响应处理记录；被选中的响应者能看自己的结果并进入 Order；未选者只能看自己的处理结果；第三方不能查看 Order 私密数据。
- 未关联 Order 的历史公开响应可只读展示；已关联正式订单的响应详情对第三方隐藏。
- Demand 与 Order 页面必须有清晰的双向上下文入口；进入履约阶段后，实际履约操作在 Order 详情页进行。

### 主要页面
- 发现：首页需求流、分类、搜索和筛选。
- Demand 详情：根据类别设计不同内容结构，而不是只换标题。
- Order 详情：保留完整履约信息，但按订单来源区分任务履约型与选择响应型。
- 发布需求：先进入类型选择页；该页有视觉明显、独立的“AI 帮我整理需求”入口；普通选择类型与 AI 路径最终进入同一套可编辑表单。
- 我的互助：**待办优先**，再区分“我发布的需求”“我参与的响应/报名/回答”“正式订单”。不再把无 Order 的 Demand 伪装成订单占位记录。
- 消息：承担事件通知，不等同于待办；通知用于告知和跳转，业务操作在对应页面完成。
- 公开个人主页与私有个人中心分离。公开主页突出信用分、真实完成正式订单数量、收到的公开评价；评价优先，下面提供独立的“查看其公开需求”列表入口。信用分不等于平均星级；无评价的新用户不能被误读为有大量好评。
- 管理员后台独立布局，路由与后端权限均需正确授权。



### 角色、阶段与内容正确性（全项目硬性约束）

**每一条展示内容、提示语、状态标签和操作按钮，都必须同时满足：当前业务对象 + 当前业务阶段 + 当前用户与对象的关系/权限 + 当前允许执行的任务。** 不能只按 `USER/ADMIN` 角色判断，也不能只按页面或状态枚举判断。一个普通用户在不同页面可能分别是需求发起方、响应者/留言者、被选中的参与者、未被选中的参与者、订单需求方、接单方或第三方访客；这些身份必须分别处理。管理员使用独立的审核/仲裁体验，不得混入学生端常规按钮。

#### 必须区分的对象关系
- **需求发起方**：管理自己的 Demand，查看自己有权查看的所有响应，选择响应者/组队成员或采纳回答，并进入自己关联的 Order（仅适用时）。
- **接单方/履约方**：处理自己实际参与的 Order，看到自己当前阶段可执行的开始、提交凭证、确认等动作；取消规则为只有接单方能在后端允许的阶段取消。
- **响应者/留言者/回答者**：只能看到自己的响应状态与对自己开放的后续操作；被选中并关联 Order 后可进入自己的订单；未被选中者不能查看别人的订单私密内容。
- **第三方访客/其他学生**：只查看公开信息与允许公开的历史响应；不能看到已关联正式 Order 的响应详情、联系方式、接单备注、完成凭证、仲裁材料、私密身份字段，也不能获得订单操作入口。
- **管理员**：在独立后台执行授权范围内的审核、管理或仲裁操作；不能把学生端普通操作按钮原样显示给管理员，也不能因前端路由可达就推定有权限。
- **匿名需求相关角色**：只有满足现有匿名查看规则的用户才可识别发起方；不能通过头像、主页链接、评价、响应列表或订单关联间接暴露匿名身份。

#### Demand / Response / Order 的展示阶段
- `Demand` 详情负责需求内容与公开互动；`DemandResponse` 负责响应/报名/回答状态；`Order` 详情负责正式一对一履约。不得用“订单占位符”表现尚未生成 Order 的 Demand。
- Demand 处于开放响应阶段时，只有适用模式才显示响应/报名/回答入口；一旦 `SELECT_ONE` 已创建 Order，关闭新增响应与选择入口；页面给发起方及被选中者提供有权限的订单入口。其他访客只看到合理的公开状态概览，不看到已关联订单的响应详情。
- `SELECT_MANY` 的目标人数、已选人数、待选报名数必须含义明确，不能混用“报名人数”和“已选人数”；达到目标后展示已完成状态，不再继续呈现报名/选人操作。
- `HELP` 的回答、采纳结果和解决状态留在 Demand；不得虚构 Order、订单履约或订单仲裁流程。
- Order 状态与操作必须结合参与者身份及完成确认子状态判断。`IN_PROGRESS` 不等于“双方都尚未确认”；接单方已确认、等待需求方确认时，不得再提示接单方重复提交，也不得向尚不符合条件的一方显示不能执行的完成操作。仲裁中、完成、取消状态不显示普通履约操作。
- 已取消 Order 会关闭关联 Demand；原 Demand 不重新开放。历史页面只读展示，不再显示接单、响应、选人等活跃操作。
- 通用提示不能误报另一角色的行为。例如对接单方说“你已提交，等待需求方确认”，对需求方说“接单方已提交，等待你确认”；仅在事实与当前身份相符时使用“你”。不向第三方展示为参与方定制的“你已…”文案。

#### 展示与提示语必须准确
- 禁止把原始内部枚举（如 `PENDING`、`SELECT_ONE`、`IN_ARBITRATION`）直接暴露给普通用户；使用统一、按业务语境映射的中文文案。相同状态在不同页面与角色下可以有不同说明，但底层业务含义必须一致。
- 对每个页面建立清晰的显示条件表：**对象类型 × 类别/交互模式 × 业务状态/子状态 × 当前用户关系 × 可见信息 × 允许操作 × 提示文案**。开始编码前先列出关键页面的角色/状态展示矩阵，作为实现与测试依据；关键显示逻辑集中定义或用类型安全的派生 view model 表达，避免每个组件各写一套互相冲突的判断。
- 不要通过猜测、默认值或解析展示文案来推断业务权限/状态；优先使用后端权威字段及真实状态历史。若数据契约不足以安全区分某种情形，应明确报告并提出最小必要 API 补充，而不是编造字段或以 UI 规避授权。
- 同一任务或状态变化不能在页面多个区域重复显示相同提示或重复操作；Demand 页负责公开需求阶段，Order 页负责履约阶段，通知只负责事件告知，待办负责当前行动。
- 禁止超前展示：例如未被选中前不得显示已接单；未创建 Order 前不得显示订单编号或订单详情入口；未上传凭证前不得显示“已提交凭证”；未完成结算前不得显示“已结算”。
- 禁止过时展示：页面切换 ID、操作成功或刷新后，必须重新获取/同步权威数据，清理旧对象的局部状态，避免将上一条需求/订单的标题、提示、按钮、响应人或凭证闪现/残留在当前页面。路由参数变化需要触发正确加载；请求失败要显式显示错误/重试，不能回退到过期缓存并装作成功。
- 禁止重复操作：提交中防重复点击；成功后同步相关 Demand、Response、Order、待办与通知视图；按钮是否显示/禁用、提示文案与服务端权限校验必须一致。不能只隐藏按钮而不做服务端授权。
- 每个空状态必须针对当前对象、角色和阶段撰写。例如“还没有人响应”“你还没有报名”“当前没有待处理事项”不能混用；无记录、加载失败、无权访问、记录已关闭是不同状态，不能全部显示成“暂无数据”。

#### 桌面 Web 范围
- 本项目现阶段只面向电脑浏览器。主要优化桌面端层级、横向空间利用、内容信息密度、键鼠交互和多栏布局；常见笔记本、1280–1440px 及以上视口是主要验收环境。
- 需要对浏览器窗口缩窄时做合理降级，避免遮挡、溢出或按钮不可达；但不要求为手机构建独立导航/卡片模式，也不以移动端适配消耗本阶段主要工作量。

## 3. 技术与视觉方向

当前技术基础为 Vue 3 + TypeScript + Vite + Vue Router + Pinia + Vitest。优先采用：
- **Tailwind CSS v4**：布局、响应式和样式 token。
- **shadcn-vue**：挑选并纳入项目自己的基础组件源码，可按设计系统调整；不要整套复制默认主题而不定制。
- **Lucide 的 Vue 图标集成**：全站统一图标线条和尺寸。落地前检查当前 shadcn-vue 生成器支持的 Lucide 包版本，锁定一个实现，不混用新旧包。
- 保留 Pinia 和现有 API 层；不为视觉重构大规模改写所有异步状态。仅在确认某模块的请求缓存、错误和失效管理确实难以维护时，再单独评估 TanStack Vue Query。
- 动画优先用细腻的 CSS transition；只有有明确收益时再添加动画库。

建议的初始视觉方向：暖中性浅背景、白色内容层、深校园绿作为主色，奖励信息使用克制的琥珀色强调，状态色遵循统一语义并保证文字对比度；采用清晰的中文排版、稳定的内容最大宽度、统一间距与圆角尺度、轻量边框和细腻 hover/focus 状态。首页不做占据首屏的大型营销 Hero，尽快让用户看到需求内容；卡片图片是内容主体，而不是装饰。不要堆叠渐变、玻璃拟态、强阴影、emoji 图标或大量彩色徽章。优先使用系统中文字体栈，避免为了“现代感”引入不必要的远程字体请求。

设计系统必须统一定义：颜色与语义状态 token、字体层级、间距、容器宽度、圆角、阴影、断点、焦点样式，以及按钮/输入框/卡片/标签/头像/弹窗/提示/骨架屏/空状态/错误状态等基础组件。

所有页面需要真实的加载中、空数据、请求失败、重试、禁用、提交中和操作成功状态。接口失败不能被显示成“没有数据”；敏感信息必须由后端权限控制，不能只靠前端隐藏。

## 4. 总控 Prompt（先发给编码 AI，作为整个项目的约束）

> 请基于 `wonder37-debug/CampusHub` 当前 `main` 分支，按本文件已确定的产品和业务规则，对 Vue 3 + TypeScript 前端进行渐进式重构。目标是现代校园社区的信息发现体验与清晰的互助服务流程。先检查现有代码和接口，再实施当前指定阶段；不要一次性重写所有页面，不要仅做换色或套用默认组件主题。
>
> 使用统一设计系统，遵循本方案中的页面地图和 Demand/Response/Order 业务边界。保持现有 API 契约和业务状态机，除非有经过验证的必要缺口；如果已确认的业务规则与当前后端权限实现不一致（例如订单仅接单方可取消、已选响应对第三方隐藏），必须以最小必要的后端授权修正和测试保证规则真实生效，不能只在前端隐藏按钮。不得虚构后端字段、统计结果或 AI 能力。把本文件“角色、阶段与内容正确性”作为不可妥协的验收契约：对每个关键页面，显式核对业务对象、状态/子状态、当前用户关系、可见信息、可执行操作与对应提示语；杜绝超前、过时、错角色和重复显示。不要用前端猜测替代权威状态与后端授权。当前仅面向桌面 Web，以常见笔记本及 1280–1440px 以上视口为主，不把手机端改造作为目标。保持真实登录、权限、匿名和私密数据边界；错误/加载/空状态必须可区分。每阶段完成后运行 `npm run type-check`、`npm test` 和 `npm run build`，检查受影响的核心路径，报告主要文件改动、测试结果、未解决问题，再等待下一阶段指令。

## 5. 分阶段实施 Prompts

### 阶段 1：设计系统与全站外壳

> 实施 CampusHub 前端重构阶段 1：建立统一设计基础与导航外壳。按官方兼容说明接入 Tailwind CSS v4、shadcn-vue 和单一的 Lucide Vue 图标集成；不要再引入第二套完整 UI 库。建立可维护的颜色、排版、间距、容器、边框、圆角、阴影、断点和状态 token，制作 Button、Input、Badge、Card、Avatar、Dialog、Tabs、Toast、Skeleton、Empty/Error 等共享组件。建立学生端社区导航外壳和独立管理员外壳；学生端身份提示、一级导航与后台管理入口需根据实际权限呈现。仅优化桌面 Web，以常见笔记本与 1280–1440px 以上视口为主。先只迁移必要公共样式，不在本阶段重做所有业务页面；移除冲突样式时确保现有页面仍可用。运行类型检查、测试和构建。

### 阶段 2：首页与需求卡片

> 实施阶段 2：重构发现首页与需求卡片。采用中等密度的混合需求流，以桌面三列为主，窗口较窄时合理降为两列的规则网格；图片统一 4:3、卡片高度尽量一致、图片懒加载且使用真实上传内容，无图时使用中性占位。卡片底部显示发布者头像与昵称、校区/时间等辅助信息；点击头像昵称进入公开主页，卡片其他区域进入 Demand 详情。按二手、组队、任务委托、求助类型突出各自的业务信息。即使卡片视觉统一，也要按访客、发布者本人、匿名需求和需求状态决定哪些身份、状态、操作提示可见；不向第三方暴露 Order 关联响应详情。整理分类、搜索、校区、排序与更多筛选层级，明确展示友好状态文案，不把 Demand 叫作 Order。不得用虚构数据或假图片填充线上卡片。

### 阶段 3：差异化 Demand 与 Order 详情

> 实施阶段 3：重构需求详情和正式订单详情。Demand 详情至少区分任务委托（快递/跑腿）、二手物品展示、学习辅导服务、活动组队、互助问答五种内容体验；同时依据交互模式和实际状态展示响应、选人、人数进度或回答/采纳模块。Order 详情只处理真实正式订单，按任务履约型与 SELECT_ONE 选择响应型区分主体内容，保留接单方上传凭证并确认、需求方二次确认、现有超时规则和仲裁机制。取消订单只有接单方可操作；取消会关闭关联 Demand，不允许在原 Demand 上重新开放。Order 创建后，Demand 提供清楚的“查看正式订单”入口，履约操作转入 Order。对发起方、接单方、被选中响应者、未选中响应者、第三方和管理员，逐项核对状态、可见内容、可执行操作、角色化提示语；避免“你已…”向错误对象展示、完成确认重复提示、过时缓存和重复按钮。严格执行响应可见性和私密凭证权限规则；若当前后端 API 会向第三方返回已关联订单的响应详情，做最小的服务端权限修正和测试，不可仅用前端隐藏代替授权。

### 阶段 4：发布流程与 AI 入口

> 实施阶段 4：重构发布需求入口。先展示需求类型选择，另设视觉明显、与普通分类卡片区分的“AI 帮我整理需求”入口。普通路径选类型后进入相应表单；AI 路径生成结构化草稿后，确认/修正类型并回填同一套可编辑表单。类型决定参与方式：EXPRESS/ERRAND 为 DIRECT_ACCEPT，SECOND_HAND/STUDY_TUTORING 为 SELECT_ONE，TEAM_UP 为 SELECT_MANY，HELP 为 HELP，只有 OTHER 可选择允许的模式。AI 不得静默覆盖用户手工确认字段或自动发布需求。先核对现有 AI API 的真实能力；若后端仅支持单次草稿生成，不要在 UI 假装支持完整多轮记忆对话。保留草稿保存、字段校验、图片上传、提交反馈和离开保护。表单提示、必填项和字段说明必须按所选需求类型呈现；切换类型时清理不再适用的字段与错误。对 AI 路径明确区分“AI 建议”“用户确认”和“已发布”，禁止把草稿状态提示成已发布，或让旧草稿字段/错误残留到新类型。

### 阶段 5：“我的互助”与通知中心

> 实施阶段 5：重构个人工作台和消息。工作台采用待办优先，待办只聚合当前用户确实需要行动的业务事项，而不是把未读通知直接当待办。下方分开呈现我发布的 Demand、我参与的 Response（报名/响应/回答）和真实 Order；移除 DemandPlaceholderOrder 等把需求伪装成订单的结构。订单列表只显示真实 Order，并明确需求方/接单方视角。通知中心按互动、订单履约、系统消息分类，负责告知和导航，不在通知列表中复制所有业务操作。所有卡片、按钮、待办标题、空状态和提示语必须根据当前用户与业务对象的真实关系、服务端状态和待执行任务生成。发布者、响应者、被选中/未选中者、接单方及管理员文案分别校准；同一待办不得重复出现在多个区块并引发重复操作。刷新或操作后同步相关业务视图，禁止保留已过时的待办或状态。

### 阶段 6：公开主页、私有个人中心与管理员后台

> 实施阶段 6：拆分公开个人主页、本人个人中心和管理员后台。公开主页显示公开身份资料、信用分、真实完成正式订单数、收到的公开评价；评价优先展示，查看其公开需求进入独立列表页。解释信用分的含义，明确它不等同于平均星级；无评价需显示无记录而非误导性评价。公开需求列表复用需求卡片系统，并由后端过滤匿名内容和不允许公开的需求。本人个人中心保留账户管理和私密字段，不得公开学号、联系方式、余额等。公开评价、匿名需求、评价人身份与订单关联信息必须分别验证公开范围，不因某条内容公开就扩大其他内容的可见范围。管理员使用独立外壳和正确的前端角色路由保护，同时依赖后端授权作为最终边界。

### 阶段 7：视觉收口、无障碍与业务回归

> 实施阶段 7：对已重构页面做整体视觉收口和回归验证。统一导航、排版层级、间距、焦点状态、空/错/加载状态、表单校验与成功反馈；以桌面 Web 为主要验收环境（常见笔记本和 1280–1440px 及以上视口），验证关键页面在窗口缩放和较窄桌面视口下仍可用；不把手机端适配作为本轮交付目标。检查键盘导航、可见焦点、语义化标题、颜色对比、图片懒加载和布局稳定性。使用现有 Vitest 覆盖组件/业务边界；为核心路径增加 Playwright 端到端验证（若运行环境允许）：直接接单履约、SELECT_ONE 留言选择后转 Order、组队选择至完成、HELP 回答采纳、订单双方确认/仲裁、取消后 Demand 关闭、公开主页隐私边界。对每个关键流程至少覆盖发起方、接单方/被选中者、未选中者和第三方；管理员另测审核/仲裁权限。验证提示语的主语/等待对象正确、没有超前/过时/重复内容，路由切换与刷新后没有旧数据残留。主要验收桌面 Web（常见笔记本、1280–1440px 及以上）和窄桌面窗口。修复发现的问题，执行类型检查、测试和生产构建。不要用截图好看代替业务验证。

## 6. 每阶段验收标准

- 页面视觉明显现代化且属于同一产品；不是默认管理后台主题，也不是纯 CSS 换色。
- 不存在 Demand 与 Order 混类；每个业务流程的页面、入口和可执行操作正确。
- 关键页面均有角色/状态矩阵；发起方、接单方、响应者/留言者、被选中/未选中者、第三方、管理员得到符合当前阶段的内容和差异化提示。
- 不出现错误对象的“你已…”文案、无法执行的按钮、超前/过时状态、重复提醒/操作或前一条记录残留。刷新、路由 ID 变化、操作成功后与后端权威数据一致。
- 数据不完整、加载失败和真正的零记录能够区分；不虚构图片、统计和状态。
- API 调用、权限、匿名身份、订单凭证和仲裁信息安全边界没有被前端改动破坏。
- 桌面 Web 是主要验收目标：常见笔记本、1280–1440px 及以上视口下布局完整，窗口缩放时不出现内容遮挡或操作不可达；本轮不要求专门设计手机端。关键操作有键盘焦点和明确反馈。
- `npm run type-check`、`npm test`、`npm run build` 通过；如有不能通过项，明确报告原因，不隐瞒、不宣称完成。
